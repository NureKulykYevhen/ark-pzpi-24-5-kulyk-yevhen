2 ЗАВДАННЯ
Відповідно до методичних вказівок до практичних занять необхідно обрати мову програмування, дослідити основні рекомендації для написання якісного коду цією мовою, продемонструвати ці рекомендації на прикладах коду, обґрунтувати кожну рекомендацію та надати детальні пояснення. Для кожного прикладу мають бути наведені фрагменти коду.
Мета роботи – ознайомитися з основними рекомендаціями щодо написання чистого, ефективного та підтримуваного коду, навчитися аналізувати код і покращувати його якість.
Обрана мова програмування: C#. Відповідно до завдання результати роботи представлено у вигляді доповіді, презентації з 12 слайдів українською мовою (додаток Б), відеозапису доповіді тривалістю 7–9 хв, завантаженого на YouTube (додаток А), та цього звіту, оформленого відповідно до ДСТУ 3008:2015. Програмний код прикладів розміщено в репозиторії GitHub (додаток В).
У доповіді та звіті розкрито питання з переліку питань для розгляду на тему «Правила оформлення програмного коду»: значення стандартизації коду для команди розробників; структура коду; форматування коду; іменування; коментарі; документування коду; конвенції стилю кодування для конкретних мов; розробка через тестування (TDD); інструменти та автоматизація для підтримки якості коду; приклади оформлення коду та їх обговорення; висновки й рекомендації щодо застосування правил.

3 ОПИС ВИКОНАНОЇ РОБОТИ
3.1 Обрана мова програмування та значення правил оформлення коду
Для дослідження обрано мову C# – сучасну об’єктно-орієнтовану мову програмування зі строгою статичною типізацією, розроблену компанією Microsoft для платформи .NET. C# застосовують для створення серверних застосунків і веб-API (ASP.NET Core), настільних програм, ігор (Unity) та хмарних сервісів. На правила оформлення коду впливають такі особливості мови: властивості як окремий вид членів класу, вбудована підтримка асинхронного програмування (async/await), мова запитів LINQ, механізм nullable reference types для контролю null-значень і XML-коментарі для документування.
Основним джерелом рекомендацій є офіційні конвенції Microsoft для мови C# [1, 2], сформовані на основі стилю коду команди .NET Runtime [3] та настанов з проєктування бібліотек Framework Design Guidelines [4]. Компілятор ці конвенції не перевіряє, проте вони є фактичним галузевим стандартом. Загальні принципи чистого коду розглянуто за [5, 6].
Програмний код читають значно частіше, ніж пишуть, тому для команди розробників важлива стандартизація коду – дотримання всіма учасниками одного набору правил, зафіксованого в стильовому посібнику та в налаштуваннях інструментів. Дотримання єдиного стилю кодування дає такі переваги:
– читабельність – однакові відступи, імена та структура дозволяють сприймати код логічними блоками, не відволікаючись на його форму;
– підтримуваність – будь-який розробник може супроводжувати будь-який модуль, а рецензування коду зосереджується на логіці, а не на суперечках щодо відступів і назв;
– мінімізація помилок – частина правил (обов’язкові фігурні дужки, контроль null-значень) прямо запобігає типовим дефектам, а аналізатори виявляють порушення ще до запуску програми.
Приклади коду в роботі побудовано на предметній області програмної системи для моніторингу резервних систем живлення, що розробляється в межах лабораторних робіт з дисципліни. Система відстежує рівень заряду акумуляторів, ступінь їх зношення та прогнозує час автономної роботи. Для кожної рекомендації наведено поганий приклад (порушення рекомендації), гарний приклад (код, що їй відповідає) та пояснення: чому правило важливе для мови C#, до яких наслідків призводить його недотримання та як воно впливає на подальший супровід коду. Повний програмний код наведено в додатку В.
3.2 Структура коду
Рекомендація: розміщуйте один публічний тип в одному файлі, назва якого збігається з назвою типу; використовуйте оголошення простору імен на рівні файлу (file-scoped namespace) і розташовуйте директиви using поза ним; узгоджуйте простори імен зі структурою каталогів проєкту; розташовуйте члени класу в однаковому порядку: константи, поля, конструктори, властивості, публічні методи, приватні методи; великий проєкт розділяйте на модулі (проєкти рішення) за шарами архітектури [1, 3].
Пояснення: відповідність назв файлів, типів і каталогів дозволяє знаходити потрібний код без пошуку по всьому рішенню, а однаковий порядок членів – одразу бачити в будь-якому класі поля на початку й допоміжні методи наприкінці. Директиви using усередині простору імен залежать від контексту й після додавання нової залежності можуть почати посилатися на інший простір імен. Клас-«звалище» на кшталт Utils із десятками не пов’язаних методів порушує принцип єдиної відповідальності: зміна однієї функції вимагає повторного тестування всього модуля [5]. Коментарі для структурування коду – розділювачі на кшталт «///// FIELDS /////» і директиви #region – у C# не рекомендовані: потреба ділити клас на секції свідчить про те, що його слід розділити на кілька класів.

3.3 Форматування коду
Рекомендація: використовуйте відступ з чотирьох пробілів без символів табуляції; застосовуйте стиль фігурних дужок Allman, за якого кожна дужка розміщується на окремому рядку; записуйте лише один оператор і одне оголошення в рядку; завжди використовуйте фігурні дужки в конструкціях if, for, while навіть для одного оператора; відокремлюйте методи та логічні блоки порожнім рядком; обмежуйте довжину рядка 100–120 символами й переносьте довгі вирази перед оператором з додатковим відступом [1].
Пояснення: форматування відображає структуру програми: за відступами читач бачить вкладеність, а за порожніми рядками – межі логічних блоків. Код, записаний в один рядок, важко читати й налагоджувати: на окремий оператор неможливо поставити точку зупину, а будь-яка зміна в системі контролю версій зачіпає весь рядок. Пропущені фігурні дужки – класичне джерело помилок, коли оператор, доданий під if пізніше, фактично виконується безумовно. Довгий рядок не вміщується в редакторі з розділеним екраном та в інтерфейсі рецензування GitHub. Вирівнювання оголошень «у колонки» додатковими пробілами не застосовують: після перейменування однієї змінної доводиться змінювати сусідні рядки, і в історії змін з’являються правки, не пов’язані зі змістом.
Відступи в різних мовах. У C#, як і в Python за PEP 8, використовують чотири пробіли; у Java, C++ та JavaScript за посібниками Google та Airbnb – два пробіли [7–9]; стандартний форматувальник мови Go використовує символи табуляції. Головне правило – не змішувати табуляцію і пробіли в одному проєкті, оскільки різні редактори відображають табуляцію різною шириною. Тому тип і розмір відступу фіксують у файлі .editorconfig (додаток В, В.4).
Стиль дужок. У стилі K&R відкривна дужка залишається в кінці рядка з оголошенням (Java, JavaScript, C++ у стилі Google); у стилі Allman кожна дужка розміщується на окремому рядку, тому межі блоку розташовані на одній вертикалі. Жоден зі стилів не є об’єктивно кращим, але для C# прийнято стиль Allman [1, 3], і код в іншому стилі виглядає незвично для інших C#-розробників.
Поганий приклад:
1  public class AlertService {
2    public void Check(Battery b) { if (b.ChargePercent < 20) { Send(b); }
3    if (b.TemperatureCelsius > 45) Send(b); }
4    void Send(Battery b) {Console.WriteLine("Alert: " + b.Id);}
5  }
Гарний приклад:

3.4 Іменування
Рекомендація: використовуйте PascalCase для типів, методів, властивостей і констант; camelCase – для параметрів і локальних змінних; camelCase з префіксом «_» – для приватних полів; починайте назви інтерфейсів з літери «I», завершуйте назви асинхронних методів суфіксом «Async», а логічним змінним і властивостям давайте префікси Is, Has, Can; давайте змістовні імена без скорочень і за потреби вказуйте в імені одиницю виміру; замість «магічних» чисел використовуйте іменовані константи та перелічення [2, 4].
Пояснення: у C# стиль регістру несе смислове навантаження: за першою літерою та префіксом видно, чи є ідентифікатор частиною публічного API, локальною змінною чи внутрішнім станом об’єкта. В інших мовах прийнято інші конвенції: snake_case для функцій і змінних у Python, UPPER_SNAKE_CASE для констант у Java та Python [7, 8], тоді як у C# константи записують у PascalCase. Перенесення звичок з інших мов – типова причина неоднорідного C#-коду. Ім’я має відповідати на питання, що зберігає змінна або що робить метод, без потреби читати реалізацію [5]; скорочення на кшталт d, lvl чи chk зрозумілі лише авторові в момент написання коду, а одиниця виміру в імені (ChargePercent, CapacityKwh) запобігає помилкам на кшталт порівняння відсотків із кіловат-годинами.
Під час вибору імен слід керуватися трьома принципами:
– зрозумілість – ім’я описує призначення в термінах предметної області (autonomyHours), а не спосіб реалізації (tempValue, list2);
– лаконічність – ім’я не містить слів, що дублюють контекст: у класі Battery властивість називається CapacityKwh, а не BatteryCapacityKwh;
– унікальність – одна сутність скрізь називається однаково, а різні сутності мають помітно різні назви.
Число 20 у виразі charge < 20 нічого не повідомляє читачеві, а якщо поріг використовується в кількох місцях, під час його зміни легко оновити лише частину входжень. Іменована константа документує значення й змінюється в одному місці; набір пов’язаних значень оформлюють переліченням (enum), а параметри, що залежать від середовища (пороги для різних об’єктів), виносять у файл конфігурації.

3.5 Коментарі
Рекомендація: коментуйте причину рішення («чому»), а не дію, яку видно з коду («що»); розміщуйте коментар на окремому рядку перед фрагментом, до якого він належить, починайте його з великої літери після одного пробілу та завершуйте крапкою; не залишайте закоментований код і не ведіть у коментарях журнал змін [1, 5].
Пояснення: коментар, що пояснює код («множимо на 100»), переказує синтаксис, не несе інформації й застаріває під час змін, вводячи читача в оману [5]. Коментар, що пояснює логіку, містить знання, якого немає в самому коді: обґрунтування неочевидного рішення, посилання на вимогу чи паспорт обладнання, попередження про наслідки зміни. Щоб уникнути надлишкових коментарів, вираз, який потребує пояснення «що він робить», виносять у змінну чи метод із промовистою назвою; закоментований код видаляють, оскільки історію змін зберігає Git; потреба в коментарях після закривних дужок («} // end if») свідчить про надто довгий метод.
Поганий приклад:
1  // метод
2  //рахує
3  public double Calc(Battery b) // повертає double
4  {
5      // множимо на 100
6      return b.Cycles / b.MaxCycles * 100;

1  public double CalculateWearPercent(Battery battery)

Рекомендація: документуйте публічні типи та члени XML-коментарями (///): опишіть призначення (<summary>), кожен параметр (<param>), значення, що повертається (<returns>), винятки (<exception>) і за потреби приклад використання (<example>); вмикайте параметр GenerateDocumentationFile, щоб компілятор попереджав про незадокументовані публічні члени [10].
Пояснення: у різних мовах для документації використовують спеціалізовані коментарі: Javadoc (/** ... */ з тегами @param і @return) у Java, рядки документації (docstrings) у Python, коментарі Doxygen у C++. У C# стандартом є XML-коментарі: компілятор перевіряє їх структуру, IntelliSense показує опис під час набору коду, а інструменти DocFX або Doxygen генерують з них довідковий сайт. Для класу документують його відповідальність, для методу – дію, параметри з одиницями виміру, значення та винятки, для модуля (проєкту) – призначення й залежності у файлі README.md. Без документації користувач класу змушений читати реалізацію, щоб дізнатися одиниці виміру й можливі винятки.

3.7 Специфічні конвенції мови C#
Рекомендація: використовуйте ключові слова мови (string, int) замість типів .NET (String, Int32), а var – лише тоді, коли тип очевидний із правої частини присвоєння; пишіть короткі методи, що виконують одну дію, з перевіркою параметрів на початку (guard clauses); перехоплюйте лише конкретні винятки, для повторного викидання використовуйте throw; без аргументу, а ресурси звільняйте оператором using; вмикайте nullable reference types; не використовуйте async void і не блокуйте асинхронний код через .Result [1, 11, 12].
Пояснення: ці правила пов’язані з особливостями платформи .NET. Глибока вкладеність умов змушує утримувати в пам’яті кілька гілок, а загальний Exception з повідомленням «error» не повідомляє, який параметр некоректний [11]. Конструкція throw ex; перезапускає трасування стека, через що місце помилки втрачається, а без using файл чи з’єднання залишаються відкритими у разі винятку. Увімкнений nullable-контекст переносить перевірку на null на етап компіляції й запобігає NullReferenceException – одному з найпоширеніших дефектів .NET-програм [12]. Виклик .Result блокує потік і в застосунках з контекстом синхронізації спричиняє взаємне блокування. C# поєднує об’єктно-орієнтований і функціональний стилі: класи отримують залежності через конструктор у вигляді інтерфейсів, а колекції обробляють запитами LINQ без побічних ефектів [4]. Оптимізацію продуктивності виконують лише після вимірювання, проте відомих неефективних конструкцій – конкатенації рядків у циклі замість StringBuilder, повторного перебору одного запиту LINQ – уникають одразу.
Поганий приклад:
 1  public double GetAutonomy(Battery b, double load)
 2  {
 3      if (b != null)
 4      {
 5          if (load > 0)
 6          {
 7              double e = b.CapacityKwh * b.ChargePercent / 100
 8                  * (1 - b.WearPercent / 100);
 9              return e / load;
10          }
11          else
12          {
13              return 0;
14          }
15      }
16      else
17      {
18          throw new Exception("error");
19      }
20  }

3.9 Розробка через тестування (Test-Driven Development)
Розробка через тестування (TDD) – підхід, за якого модульний тест пишуть до коду, який він перевіряє [13]. Робота виконується короткими циклами «червоний – зелений – рефакторинг»:
– червоний – написати тест для нової поведінки й переконатися, що він не проходить;
– зелений – написати мінімальний код, достатній для проходження тесту;
– рефакторинг – покращити структуру й оформлення коду, повторно запускаючи тести, які гарантують, що поведінка не змінилася.
Рекомендація: розміщуйте тести в окремому тестовому проєкті (PowerMonitor.Tests), структура якого повторює структуру основного проєкту; називайте тестові методи за шаблоном Метод_Сценарій_ОчікуванийРезультат; структуруйте кожен тест за схемою Arrange – Act – Assert (підготовка – дія – перевірка); перевіряйте в одному тесті одну поведінку й не розміщуйте в тестах умовну логіку; для кількох наборів вхідних даних використовуйте параметризовані тести ([Theory] та [InlineData] у xUnit) [14].
Пояснення: TDD впливає на організацію основного коду: щоб клас можна було протестувати, він повинен отримувати залежності через конструктор, мати невеликі методи з однією відповідальністю та не звертатися напряму до системного часу, файлів чи мережі. Тест, назва якого описує сценарій, виконує роль документації. Тести з умовною логікою та «магічними» значеннями важко підтримувати: після зміни вимог незрозуміло, чи помилка в коді, чи в самому тесті, і команда починає вимикати такі тести. Набір надійних тестів є передумовою безпечного рефакторингу.
Гарний приклад (тести для класу BatteryMonitor з додатка В, В.3):

3.10 Інструменти та автоматизація для підтримки якості коду
Рекомендація: фіксуйте правила стилю у файлі .editorconfig у корені проєкту; вмикайте аналізатори Roslyn і перевірку стилю під час збирання (EnforceCodeStyleInBuild); перевіряйте форматування командою dotnet format; доповнюйте перевірку статичним аналізом коду (SonarQube, Codacy) і запускайте перевірки автоматично – у Git hook перед кожним комітом та в конвеєрі CI/CD під час кожного pull request [15–17].
Пояснення: правила, які перевіряються лише вручну, з часом порушуються. Файл .editorconfig зберігається в репозиторії разом із кодом, тому всі учасники команди та IDE (Visual Studio, JetBrains Rider, Visual Studio Code) застосовують однакові налаштування, а параметр EnforceCodeStyleInBuild перетворює порушення стилю на попередження збирання. Статичні аналізатори виявляють не лише порушення стилю, а й потенційні дефекти: можливе звернення до null, невикористані змінні, надто складні методи, дублювання коду. Платформи SonarQube і Codacy зберігають історію показників якості й визначають «quality gate» – умови, без виконання яких зміни не можна об’єднати з основною гілкою [17]. Git hook pre-commit не дозволяє створити коміт із неформатованим кодом, а конвеєр CI повторює ту саму перевірку на сервері, тому правила неможливо обійти.
Файли .editorconfig і PowerMonitor.csproj, використані в роботі, наведено в додатку В (В.4). Під час перевірки коду з додатка В аналізатори не виявили жодного зауваження до коду після рефакторингу (В.1, В.3), а для коду до рефакторингу (В.2) повідомили про відсутні фігурні дужки, тип String замість string, публічне поле та простір імен не на рівні файлу. Перевірку виконує команда:
1  dotnet format --verify-no-changes

3.11 Приклади оформлення коду: аналіз та обговорення
Для узагальнення розглянутих рекомендацій їх застосовано до фрагмента класу моніторингу батарей, у якому одночасно порушено більшість правил. Код до рефакторингу наведено в додатку В (В.2), код після рефакторингу – у додатку В (В.3). Під час виправлення коду виконано такі зміни:
– назви простору імен, класу, методу та параметрів приведено до стилів PascalCase і camelCase;
– публічне поле зі скороченою назвою l замінено приватним полем _batteries, яке заповнюється через конструктор;
– «магічне» число 2 винесено в іменовану константу LowAutonomyHours;
– формулу доступної енергії перенесено в метод GetAvailableEnergyKwh класу Battery;
– рядкові результати «LOW» та «OK» замінено типізованим записом AutonomyStatus, а форматування тексту залишено інтерфейсу користувача;
– додано перевірку параметрів, nullable-анотацію та XML-документацію;
– застосовано оголошення простору імен на рівні файлу, стиль дужок Allman і впорядковані директиви using.
Зміни вносилися невеликими кроками з перевіркою після кожного кроку, а автоматичне форматування виконувалося окремо від змін логіки, щоб кожну зміну було легко перевірити під час рецензування.
Вплив чистоти коду на розв’язання задач і продуктивність команди. Початковий варіант класу (В.2) містить 21 рядок, а виправлений (В.3) – 51 рядок, проте обсяг зріс за рахунок документації, перевірок і порожніх рядків, а не логіки. Водночас виправлений код має практичні переваги: метод CheckAutonomy покривається модульними тестами (підрозділ 3.9), оскільки повертає типізований результат замість рядка; поріг низької автономності змінюється в одному місці; ситуація «батарею не знайдено» більше не маскується під звичайний результат «not found»; формулу доступної енергії повторно використовують інші сервіси. Для команди це означає швидше рецензування змін, меншу кількість дефектів у робочій версії та скорочення часу на введення нового розробника в проєкт [5, 6].

– було розглянуто значення стандартизації коду для команди розробників та основні правила оформлення програмного коду мовою програмування C#: структуру коду, форматування, іменування, коментування й документування, а також специфічні конвенції мови щодо методів, обробки помилок, контролю null-значень та асинхронного коду;
– кожну рекомендацію обґрунтовано й продемонстровано на прикладах коду з предметної області системи моніторингу резервних систем живлення;
– порівняно конвенції C# з конвенціями мов Python, C++, Java та JavaScript і встановлено, що загальні принципи чистого коду спільні для всіх мов, а відрізняються стиль регістру, відступи та розміщення дужок;
– розглянуто розробку через тестування та інструменти автоматичного контролю якості коду (.editorconfig, аналізатори Roslyn, dotnet format, SonarQube, Git hooks, CI/CD) і встановлено, що автоматизація є найефективнішим способом підтримання єдиного стилю в команді;

В.3 Приклад програмного коду після рефакторингу (клас BatteryMonitor)
GitHub репозиторій: https://github.com/NureKulykYevhen/ark-pzpi-24-5-kulyk-yevhen/blob/main/Pract1/ark-pzpi-24-5-kulyk-yevhen-pract1/Services/BatteryMonitor.cs
 1  using System;
 2  using System.Collections.Generic;
 3  using System.Linq;
 4  using PowerMonitor.Models;
 5
 6  namespace PowerMonitor.Services;
 7
 8  /// <summary>
 9  /// Відстежує стан батарей та оцінює час автономної роботи.
10  /// </summary>
11  public class BatteryMonitor
12  {
13      private const double LowAutonomyHours = 2.0;
14
15      private readonly List<Battery> _batteries;
16
17      public BatteryMonitor(IEnumerable<Battery> batteries)
18      {
19          ArgumentNullException.ThrowIfNull(batteries);
20          _batteries = [.. batteries];
21      }
22
23      /// <summary>
24      /// Оцінює автономність батареї за поточного навантаження.
25      /// </summary>
26      /// <param name="batteryId">Ідентифікатор батареї.</param>
27      /// <param name="loadKw">Поточне навантаження, кВт.</param>
28      /// <returns>Час автономної роботи та ознака низького запасу.</returns>
29      public AutonomyStatus CheckAutonomy(int batteryId, double loadKw)
30      {
31          ArgumentOutOfRangeException.ThrowIfNegativeOrZero(loadKw);
32
33          Battery? battery =
34              _batteries.FirstOrDefault(b => b.Id == batteryId);
35          if (battery is null)
36          {
37              throw new KeyNotFoundException(
38                  $"Battery {batteryId} was not found.");
39          }
40
41          double autonomyHours = battery.GetAvailableEnergyKwh() / loadKw;
42          bool isLow = autonomyHours < LowAutonomyHours;
43
44          return new AutonomyStatus(autonomyHours, isLow);
45      }
46  }
47
48  /// <summary>
49  /// Результат оцінки автономності батареї.
50  /// </summary>
51  public record AutonomyStatus(double Hours, bool IsLow);
